## 1. Executive Summary

TrustTrip has successfully implemented and verified **Implementation Wave 1: Canonical Plan → Proposed Revision + Airport Identity**. 

The authoritative contract is currently enforced:
- The initial itinerary generated by the AI planner immediately becomes **Revision #1** with status **`PROPOSED`** and a genuine UUID persisted in `plan_revisions` (`EvidenceRevisionStore`).
- Replanning monotonically advances the authoritative revision sequence (Revision #2 `PROPOSED`) under database row-level locking.
- Approved revisions proceed directly to Section 9 Booking Authorization without forcing a redundant manual "Create Revision" step.
- Natural-language destinations (e.g. `"Darjeeling, India"`) resolve to their commercial gateway airports (e.g. `"IXB"`), persisting canonical IATA codes in trip metadata while preserving human-readable destination text for UI presentation.
- All 61 backend pytest items and 100% of frontend vitest contract suites pass without error.

This audit evaluates the remaining product-flow risks, architectural boundaries, and pending waves before any further code changes are made.

## 2. Verified Architecture

The TrustTrip platform is structured into four distinct layers:

1. **Frontend Presentation & State Layer (React 18 + Vite + TypeScript):**
   - UI views (`TripDetailView`, `CreateTripView`, `FlightsView`, `HotelsView`).
   - Two-step booking workspace (`BookingWorkspace.tsx` managing flight verification and boutique stay reservations).
   - Authoritative API client (`apiClient.ts`) enforcing zero synthetic ID fabrication.
   - Flow controller service (`bookingService.ts`).

2. **API & Route Boundary Layer (FastAPI):**
   - `auth_api.py` (`/api/auth`): JWT authentication and user management.
   - `trips_api.py` (`/api/trips`): Trip CRUD, revision lifecycle, approval, and Section 9 authorization.
   - `app.py` (`/api/travel`): AI plan generation and Wave 1 revision orchestration.
   - `flight_api.py` (`/api/flights`): Flight search, offer snapshotting, and Section 5B/5C booking intent lifecycle.
   - `flight_booking_api.py` (`/api/bookings`): Alternative booking lifecycle endpoint supporting prepare, revalidate, and handoff.
   - `hotel_api.py` (`/api/hotels`): Hotel search and prebooking.
   - `hotel_payment_api.py` (`/api/hotel-payments`): Section 10 hotel Razorpay order creation and payment verification.
   - `payment_api.py` (`/api/payments`): Flight Razorpay order creation, currency conversion, and Duffel order execution.

3. **Service & Domain Layer:**
   - `services/planner_service.py` & `services/chat_planner.py`: Orchestrates AI travel plan generation.
   - `services/travel_planner.py`: Deterministic resolver mapping places and regions to IATA gateway codes (`CITY_TO_IATA`, `REGION_TO_IATA`, `INDIAN_AIRPORTS`).
   - `services/flight_search_service.py`: Extracts canonical flight criteria from trip metadata and queries providers.
   - `services/flight_booking_service.py`: Manages flight booking intents, revalidation, and Duffel order creation.
   - `services/hotel_booking_service.py`: Pre-books hotel rooms and processes bookings.
   - `services/razorpay_service.py`: Generates Razorpay orders and verifies HMAC-SHA256 signatures.
   - `services/currency_converter.py`: Performs FX conversions with deterministic rate sources.

4. **Persistence & Data Access Layer (PostgreSQL 15+ & In-Memory Fallbacks):**
   - `TripStore`: `trips`, `threads` tables.
   - `EvidenceRevisionStore`: `plan_revisions`, `plan_approvals`, `plan_revision_rejections` tables.
   - `AuthorizationStore`: `booking_authorizations` table.
   - `SearchSessionStore`: `search_sessions`, `offer_snapshots`, `booking_intents` tables.
   - `TransactionStore`: `flight_transactions` table.
   - `HotelTransactionStore`: `hotel_transactions` table.
   - `UserStore`: `users` table.

2. **Flight Payment Currency Mismatch Guard:**
   - File: [`payment_api.py`](file:///n:/Documents/GitHub/TrustTrip_TravelPlanner/payment_api.py), lines 145–156:
     ```python
     provider_currency = str(offer.get("currency") or "").upper()
     requested_currency = str(expected_currency or "").upper()
     if provider_currency != requested_currency:
         raise HTTPException(
             status_code=409,
             detail=f"The live flight currency changed from {requested_currency} to {provider_currency}..."
         )
     ```
   - **Risk:** If Duffel returns an offer in `USD` or `GBP`, and the frontend requests payment in `INR`, `POST /api/payments/create-order` will reject with 409. The client must pass the provider's currency as `expected_currency`, and let the backend convert it to INR for Razorpay checkout.
3. **Hotel Currency Flow:**
   - Prebook returns INR or provider currency; `hotel_payment_api.py` stores `amount_inr` and passes paise to Razorpay. Cleanly validated in Section 10 tests.

## 9. Revision Integrity Findings

### Verified Evidence
1. **Authoritative UUID Source:**
   - Revisions are created exclusively by `TripStore.create_revision_atomic()` using Python `uuid.uuid4()`.
   - Never synthesized on frontend. `normalizeBackendTripDetail()` returns `revisions = []` if absent.
2. **Monotonic Progression:**
   - Plan generation: Revision #1 `PROPOSED`.
   - Subsequent replan: Revision #2 `PROPOSED`.

   - Revisions cannot be modified once created.
   - Stale approval attempts (mismatched `expected_revision_number`) are rejected with 409 conflict.
   - Rejections are recorded immutably in `plan_revision_rejections` and block approval.

## 14. Bugs Identified

### [BUG-01] Hardcoded Passenger Identity in Flight Offer Selection
- **Severity:** P0 (Identity / Correctness)
- **Observed behavior:** Flight passenger data is always "Ananya Roy", born 1992-05-15, email traveler@trusttrip.com.
- **Expected behavior:** Flight passenger details should be populated from the authenticated user profile (`currentUser.full_name`, `currentUser.email`) or traveler input modal.
- **Root cause:** Hardcoded literal in `frontend/src/services/bookingService.ts:233-239`.
- **Evidence:** Verified by code inspection and grep in `bookingService.ts`.
- **Affected files:** `frontend/src/services/bookingService.ts`, `frontend/src/components/booking/BookingWorkspace.tsx`.
- **Proposed minimal fix:** Pass authenticated user or traveler details from `BookingWorkspace` into `bookingService.selectFlightOffer()`.
- **Regression risk:** Low.

### [BUG-02] Hardcoded Guest Identity in Hotel Prebooking
- **Severity:** P0 (Identity / Correctness)
- **Observed behavior:** Hotel guest is always "Ananya Roy", email traveler@trusttrip.com.
- **Expected behavior:** Hotel guest details should be populated from authenticated user profile or checkout contact form.
- **Root cause:** Hardcoded literal in `frontend/src/services/bookingService.ts:481-482`.
- **Evidence:** Verified by code inspection in `bookingService.ts`.
- **Affected files:** `frontend/src/services/bookingService.ts`, `frontend/src/components/booking/BookingWorkspace.tsx`.
- **Proposed minimal fix:** Pass user profile or contact details into `bookingService.prepareHotelBooking()`.
- **Regression risk:** Low.

### [BUG-03] Flight Booking Flow Disconnect (Direct Duffel vs. Razorpay)
- **Severity:** P1 (Product Flow Alignment)
- **Observed behavior:** `BookingWorkspace.tsx` confirms flights via `POST /api/flights/booking/{id}/confirm` (direct Duffel balance order) instead of presenting a Razorpay payment modal (`POST /api/payments/create-order`).
- **Expected behavior:** Both flight and hotel services should follow consistent checkout flows (or direct Duffel sandbox booking should be documented as the intended flight contract).
- **Root cause:** Frontend was wired to Section 5B/5C direct booking lifecycle while Section 10 payment router (`payment_api.py`) was created separately.
- **Evidence:** Grep shows 0 calls to `/api/payments/create-order` in `frontend/src`.
- **Affected files:** `frontend/src/components/booking/BookingWorkspace.tsx`, `frontend/src/services/bookingService.ts`.
- **Proposed minimal fix:** If flight payment via Razorpay is required, wire `BookingWorkspace` to use `PaymentReviewModal` for flights targeting `/api/payments/create-order`.
- **Regression risk:** Medium.

### [BUG-04] Currency Mismatch Risk in Flight Payment API
- **Severity:** P1 (Payment Correctness)
- **Observed behavior:** `_validate_and_convert_offer` in `payment_api.py:149-156` raises 409 if `expected_currency != provider_currency`.
- **Expected behavior:** Client should pass provider's native currency as `expected_currency` along with `expected_amount`, allowing backend `CurrencyConverter` to convert to INR for Razorpay.
- **Root cause:** Strict equality check prevents client from submitting INR request against a USD provider offer.
- **Evidence:** Verified in `payment_api.py:149`.
- **Affected files:** `payment_api.py`, `frontend/src/lib/apiClient.ts`.
- **Proposed minimal fix:** Ensure client sends offer's native `currency` and `price` to `create-order`, letting the backend handle conversion to INR.
- **Regression risk:** Low.
