# TrustTrip — Verified Architecture Document

**Date:** 2026-10-04  
**Status:** Post-Wave-1 Verified Architecture

## 1. Architectural Principles

1. **Authoritative Single Source of Truth:**
   - Identity for trips, revisions, approvals, snapshots, and transactions is maintained exclusively on the backend.
   - Frontend components never synthesize identity (e.g. no synthetic revision IDs or confirmation codes).
   
2. **Atomic Monotonic Revision Sequence:**
   - Every revision is created under a trip row lock (`SELECT ... FOR UPDATE` or memory lock).
   - Revisions strictly advance sequentially: `0 -> 1 -> 2 -> ... -> N`.
   - The initial plan generated by AI is Revision #1 with status `PROPOSED`.

3. **Strict Gate Ordering (HITL -> Authorization -> Booking):**
   - No booking intent or payment order can be created without an approved revision and a valid Section 9 booking authorization.
   - Any change to trip constraints (dates, destination, origin, passengers) creates a new revision and automatically invalidates prior authorizations and flight/hotel selections.

4. **Multi-Currency Safety & Conversion:**
   - Live airline and hotel rates are fetched in provider currencies (e.g. USD, GBP, EUR) and converted server-side to INR for Razorpay checkout.
   - Browser amounts are never trusted blindly; the backend rechecks provider fares before order creation.

## 2. Core Subsystems

### Subsystem 1: Trip & Revision State Machine (`TripStore` & `EvidenceRevisionStore`)
- **Trips Table (`trips`):** Contains `id`, `user_id`, `status`, `destination`, `origin`, `current_revision_id`, `current_revision_number`, `metadata`.
- **Plan Revisions Table (`plan_revisions`):** Contains immutable snapshots of constraints, plan JSON, and change diffs.
- **Approvals Table (`plan_approvals`):** Tracks human approvals bound to `(trip_id, revision_id)`.
- **Rejections Table (`plan_revision_rejections`):** Records rejection ledger preventing approval of rejected revisions.

### Subsystem 2: Travel Planning & Agent Service (`PlannerService`, `chat_planner`, `travel_planner`)
- Uses LangChain / LangGraph with Google Gemini to synthesize structured travel itineraries.
- `travel_planner.py` provides deterministic destination resolution, mapping tourist spots/hill stations to commercial gateway airports.

### Subsystem 3: Flight Booking Subsystems (Two Co-Existing Paths)
- **Direct Supplier Booking (`flight_booking_api.py` / `FlightBookingService`):**
  - Section 5B/5C contract: `prepare` -> `revalidate` -> `approve` -> `confirm`.
  - Communicates directly with `DuffelProvider` to issue airline tickets.
  - Used by the current frontend `BookingWorkspace.tsx` flight step.
- **Payment-Gated Flight Booking (`payment_api.py`):**
  - Section 10 contract: `/api/payments/create-order` -> Razorpay checkout -> `/api/payments/verify-and-book`.
  - Captures Razorpay payment before triggering Duffel order creation.

### Subsystem 4: Hotel Booking Subsystem (`hotel_api.py`, `hotel_payment_api.py`, `hotel_booking_service.py`)
- Section 6 / Section 10 hotel contract.
- Search -> Prebook (`POST /api/hotels/prebook`) -> Payment Order (`POST /api/hotel-payments/create-order`) -> Verify & Book (`POST /api/hotel-payments/verify-and-book`).
- Captures Razorpay payment and stores full reservation confirmation in `hotel_transactions`.

### Subsystem 5: Section 9 Booking Authorization Guard (`AuthorizationStore`)
- Validates 10 eligibility conditions before allowing booking order creation:
  1. User ownership
  2. Revision existence
  3. Plan approval presence
  4. Monotonic revision version matching
  5. Departure date >= today
  6. Origin / destination validity
  7. Passenger count validity
  8. Selected offer tenant isolation
  9. Snapshot constraint consistency
  10. Absence of unresolved rejections
